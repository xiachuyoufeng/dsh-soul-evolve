> 关系：本文替代 `优化方案-v0.7.md`（下称 v1），v1 保留作对照

## 0. 一句话结论

v1 的四层方向是对的，但**优先级排错了一个位置**、**漏了一整层（观测）**、**P0-1 的对象选错了地方**（指向了不在本仓库的 memory 插件）。

v2 把顺序改成：**先能看见 → 再会变脸 → 再记住重点**。

### 唯一一条贯穿全程的判据

> 一个行为能不能做，看它**是否由真实状态驱动**。
> 由状态驱动 = 表达；无状态硬做 = 表演。

这条判据在本轮已被确认并写入 Soul 面板。v1 用「不表演情绪」否决副语言表达，是对这句话的误读——**表演是伪装（无中生有），不是表达本身**。

## 2. 架构：补一层观测

现在 `state.json` 只记录每轮 `delta`，**不记 scene，也不记三旋钮**。

后果：v1 的验收标准「工作/闲聊温差 > 0.15」**算不出来**，只能靠回忆——那不是验收，是许愿。

v2 在状态层和表达层之间插入一层：

```
输入 ──▶ reflex ──▶ state ──▶ modulate(scene) ──▶ 注入文本
                        │            │
                        └────────────┴──▶ trace（只追加）──▶ stats 脚本
```

## 4. v0.7 观测层（新增 P0-0）

### 做什什么

新增 `src/trace.js`，在每轮注入时追加一行到 `~/.dsh-soul-evolve/turns.jsonl`。

```jsonc
{
  "t": 1793594048565,
  "sid": "a434b84c",          // 会话 id 前 8 位
  "scene": "work",             // v0.8 起有值，先写 null
  "state": { "valence": 0.12, "arousal": 0.21, "energy": 0.91, "intimacy": 0.25, "focus": 0.97 },
  "knobs": { "verbosity": 0.89, "warmth": 0.24, "patience": 0.94 },
  "textLen": 42,
  "panelLen": 1180,            // 注入的人格面板字数
  "reflex": ["praise"]
}
```

### 关键实现点（有坑，先写清）

1. **渲染函数会被多次调用**（重试、多轮组装都可能触发）。trace 必须按 `(sid, 秒级时间戳, textLen)` 去重，否则统计翻倍失真。
2. **写入失败绝不能影响注入**。整个 trace 用 try/catch 包住，失败静默。
3. **轮转**：文件 > 2 MB 或 > 5000 行时改名为 `turns.1.jsonl`（只保留 1 份历史）。

### 配套脚本

新增 `scripts/stats.mjs`，输出：

- 按 scene 分组的 `warmth` / `patience` / `verbosity` 均值与差值
- 面板注入字数的时间趋势（周环比）
- 各 reflex 规则命中分布
- 状态五维的分布与相关性

该脚本就是后续两个版本的**自动验收器**。

### 验收

- 跑满 50 轮后 `turns.jsonl` 行数与实际轮次一致（无重复、无漏记）
- `stats.mjs` 能输出按 scene 分组表（此时 scene 全为 null，先验通路）

## 5. v0.8 场景切面 + 副语言通道

### 5.1 场景判定（`src/scene.js`）

四类：`work` / `chat` / `support` / `tech`。**默认 `work`**。

信号来源：

| 来源 | 示例信号 |
|---|---|
| 输入特征 | 指令动词（改/修/做/查）、文件路径、代码块、问号、长度、语气词 |
| 时段 | 深夜 + 短句 → chat/support 加分 |
| 连续性 | 上一轮 scene 相同则加权（惯性） |

**滞回规则**（防逐句跳变）：

- 切换需新 scene **连续 2 轮**得分占优；
- 或单轮得分超过当前 scene **1.5 倍**才立即切。

### 5.2 基准表（`reflex.js` 的 `modulate(state, scene)` 增加 scene 参数）

| scene | warmth 偏移 | patience 偏移 | verbosity 偏移 |
|---|---|---|---|
| work | 0 | +0.15 | −0.10 |
| chat | +0.25 | −0.10 | +0.05 |
| support | +0.30 | +0.20 | −0.15 |
| tech | 0 | +0.10 | +0.10 |

最终值仍需夹紧到 `[0,1]`（现有逻辑保留）。

### 5.3 副语言 = 状态的输出通道（v1 P2-1 的正确形态）

**不给模型「往句子里塞填充词」的指令**，而是让状态自己外显：

```js
// modulate 额外返回 prosody
{ hesitation: energy < 0.35,   // 低精力 → 允许犹豫、拖长
  fragmented: focus < 0.40 }    // 低专注 → 句子更碎
```

注入文本里只写状态事实，例如：

> 你现在精力偏低（0.3）、专注度不高。表达可以更短、更犹豫，不必把句子写齐。

这样「犹豫」是被状态**逼出来**的，不是随机插入的——满足判据。**不需要独立开关**，因为状态低才有、状态高就没有。

### 验收（自动）

- `stats.mjs`：`chat` 与 `work` 的 warmth 均值差 **> 0.15**
- 场景切换频率：一天内 switch 次数 / 总轮次 **< 15%**
- 人工抽查 20 轮：无「严肃话题里卖萌」错位

## 6. v0.9 演化条目加权 + 注入预算（P0-1 重定义）

### 为什么换对象

v1 要改 memory 插件。但真正会膨胀的是**我们自己的 Soul 面板**：

- `MAX_CONTENT = 20000`，**每轮全量注入**
- `C5` 只做「超出上限归档」，**不排序**
- 演化条目只增不减 → 每轮 token 单调上涨 → 到顶后新条目写不进去

改这里只在本包内，收益一致。

### 6.1 数据结构

`personas.json` 的 card 从 `{ content, updatedAt }` 升级为：

```jsonc
{
  "content": "手写基底（Identity/Personality/…）",
  "entries": [
    { "id": "e1", "text": "…", "category": "correction|preference|scene",
      "weight": 1.0, "lastHit": 1793594048565, "createdAt": 1793594048565 }
  ],
  "history": [ { "at": …, "content": "…" } ]   // 最近 10 版，支持回滚
}
```

注入质量 = `content` + 按 weight 降序渲染的 entries（渲染时带 `〔已修正〕` 标记）。

导出 `.md` 时把 entries 追加在正文后，保持与市场 soul.md 互通的格式。

### 6.2 权重规则

| 类别 | 初始 | 半衰期 |
|---|---|---|
| `correction`（C1 明确纠正） | 1.0 | **不衰减** |
| `repeat`（重复犯错） | 0.9 | 不衰减 |
| `preference`（长期偏好） | 0.6 | 90 天 |
| `scene`（场景相关） | 0.4 | 30 天 |

命中 +0.1（上限 1.0）。

### 6.3 命中判定：务实取舍

**不做**逐轮语义匹配（成本高、易误判）。做法：

`Soul 面板 set` 写入新条目时，检查同 `category` 下关键词重叠 → 视为重复命中，旧条目 +0.1，新条目按「冲突标〔已修正〕」处理。

即：权重靠**写入时的比对**维护，不靠读取时匹配。这不是最理想，但是能在本版本内做对的最小实现。

### 6.4 注入预算

- 注入硬上限 **4000 字**（约 2500 token），`content` 优先保留，entries 按 weight 填充，超出截断
- 面板 UI 里被截断的条目标灰，显示「未注入」
- 这样「20 万字符积压」变成可控的排序问题，而不是爆炸

### 验收（自动）

- 同一批条目中，`correction` 类权重显著高于 `preference` 类（差 > 0.2）
- 注入长度稳定在 4000 字以内，连续 4 周增长 < 5%
- 面板历史可回滚到上一版（UI 上一个按钮）

## 7. v1.0 收尾项

### 7.1 主体性（P1-1 的正确落位）

**不写代码**。DSH 已有审批策略（当前会话就是 `ask`），插件里再写一套「强制确认」会打架。

正确做法：把边界写进 **Soul 面板**的 `## Boundaries` 段。这已经完成——当前面板已含「动文件先看，删改先确认路径」。

剩下唯一值得做的代码层：高危操作词表（删除/覆盖/批量/对外发送）命中时，在状态注入里追加一句提醒。成本 ~10 行，可选。

### 7.2 状态作用域

当前 `state.json` 全局单份 → 工作会话与闲聊会话互相污染。

方案：加配置 `stateScope: "global" | "workspace"`，**默认 `global`**（保留跨会话连续性这个卖点），需要隔离的人自己切。

### 7.3 面板版本历史

已在 v0.9 一并做（`history` 字段）。这是补 v1 声称已有、实际没有的能力。

## 8. 明确不做

1. **不改 memory 插件**（dsh-memory-evolve 是独立包，跨包改造不在本插件职责内）
2. **不做无条件副语言**（无状态硬插填充词 = 表演）
3. **不做响应延迟、笔误模拟**（微信场景里等于折磨用户；会被当成 bug）
4. **不做大五人格全套**（5–7 维够用，多了维护不起且无法验证）
5. **不追求「像人」的表演**（目标是行为自洽的交互对象）
