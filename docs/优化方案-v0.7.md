# dsh-soul 优化方案（v0.7 → v1.0）

> 依据：DeepSeek 对话《怎么增强 Agent 的人感》四层框架 + 本项目 v0.6.0 现状盘点
> 日期：2026-11-01
> 目标：从「会记录状态的插件」进化到「有连续人格、会被当成同事的助手」

---

## 一、结论先行

v0.6.0 已经做对了最难的部分：**人格是架构底座，不是一句提示词**——有状态层、有演化引擎、有人设卡。

但还有三处停留在"提示词水平"，按投入产出排序：

1. **记忆不分权重**（最该改）——现在所有记忆平等，久了必然变成检索机器
2. **没有场景切面**——工作、闲聊、用户低落时，语气强度几乎一样，这是僵化
3. **主体性偏弱**——很少主动说"这个我不建议""要不要先确认"

P0 两项预计 1–2 周可见效，P1 次之；副语言层**不建议照搬**（见第五节）。

## 三、差距与优先级

### P0-1 记忆的非对称权重 ⭐ 最优先

**问题**：现在 memory 条目一律平等。用户随口一句和你明确纠正我一句，权重相同。

**做法**：
- 条目增加 `weight`（0–1）与 `lastHit` 字段
- 权重来源：C1 三类事件给基准分，重复命中加成，长时间未命中衰减
- 注入时按权重排序，只注入 Top-N，其余归档
- 衰减半衰期先定 90 天，可配置

**成本**：evolve.js + memory 注入侧各改一处，约 150 行
**风险**：低。衰减算错只影响排序，不影响内容
**验收**：同一批记忆里，明确纠正类条目的权重显著高于闲聊类

---

### P0-2 场景切面

**问题**：问财报和说"可可爱爱"时，温度几乎一样 → 僵化。

**做法**：
- 增加 `scene` 判定（工作/聊天/情绪支持/技术求助），来自输入特征 + 时段 + 对话连续性
- 同一人格，不同场景给不同调制基准：工作=低温度高耐心，聊天=高温度低耐心
- 场景切换有惯性，不逐句跳变

**成本**：reflex.js 增加判定与基准表，约 120 行
**风险**：中。判错场景会导致语气错位（在严肃话题里卖萌最忌讳）
**验收**：连续一周里，工作/闲聊两类对话的调制值域有明显分离（温差 > 0.15）

---

### P1-1 主体性边界

**问题**：现在几乎有求必应，缺少"要不要先确认"的停顿。

**做法**：
- 高风险操作（删除、覆盖、批量改动、对外发送）前强制确认，不是建议而是规则
- 不确定时用提问引导代替报错（已在做，写进规则固化）
- 允许拒绝：明显有害或违背边界的请求，给理由后拒绝

**成本**：规则化，几乎无代码
**风险**：低，但过度会显得推诿
**验收**：一个月内至少出现一次"我先确认一下"式停顿，且用户没有反感

---

### P2-1 副语言层（建议小范围实验，默认关）

**问题**：即时、均匀、完美的回复是 AI 味最浓的信号。

**做法**：只在明确检测到"闲聊场景"时开启，且幅度极小
- 偶尔的填充词（"嗯…""那个"）
- 句长不齐（不要每句都同样长）
- 上下文回指（自然提起之前话题）

**成本**：低
**风险**：**高**。文字里做延迟/笔误极易变成刻意卖萌，微信场景尤其危险
**建议**：做成开关，默认关闭，先自己观察一周

---

### P2-2 视觉与空间化输出

纯文本是 AI 的舒适区，不一定是人的。复杂结构优先给图/表，而不是长文。

**成本**：中（依赖现有 Office/渲染能力）
**优先级**：等前四项稳定后再说

## 五、明确不做（避免做偏）

1. **不照搬响应延迟**——微信场景里人为延迟等于折磨用户，且平台本身已有延迟
2. **不做笔误/错字模拟**——用户会当成 bug，而不是人味
3. **不做大五人格全套**——5–7 个维度够用，多了维护不起，且无法验证
4. **不追求"像人"的表演**——目标是"行为自洽的交互对象"，不是角色扮演

---

## 六、验收标准

一句话标准（来自原文，我认为最准）：

> 如果这个 Agent 离职了，用户会不会觉得失去了一个"同事"，而不仅仅是关掉了一个工具。

可量化三条：

- [ ] 记忆条目有权重，且能在 90 天内观察到衰减
- [ ] 工作/闲聊两类对话的调制值域分离明显（温差 > 0.15）
- [ ] 一个月内至少一次"我先确认一下"式停顿，且用户没有反感
